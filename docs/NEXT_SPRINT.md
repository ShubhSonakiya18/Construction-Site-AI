## Sprint 16 Goal

Per `docs/ROADMAP.md`'s Phase 5 plan: "Spanish, Portuguese, Mandarin, French support — critical for USA residential construction workforce demographics."

**This is a smaller, more contained gap than it first looks, but not a no-op.** The other two remaining Phase 5 items were checked and ruled out before this sprint's scope was chosen: Defect Detection needs photo/image upload infrastructure that doesn't exist anywhere in this codebase and a first-ever computer-vision integration (this app has only ever called Groq LLM + local faster-whisper transcription — no image model, no photo upload endpoint); Bid Estimation's premise ("historical project data → bid estimate") is currently unsupportable since **exactly one project exists in the entire database** — there is no real history to learn from yet. Voice Note Multi-Language Support, by contrast, sits on real, already-working infrastructure that was investigated in detail before writing this spec:

- **Transcription is already multilingual with zero code changes needed.** `speech/whisper/engine.py` calls faster-whisper's real `.transcribe()` with `language=cfg.language` (default `None` = auto-detect) and `task=cfg.task` (default `"transcribe"`) — both wired through from `speech/utils/constants.py`'s `DEFAULT_LANGUAGE`/`DEFAULT_TASK`. Whisper's `base`/`medium` models are inherently multilingual (trained on ~100 languages including Spanish, Portuguese, Mandarin, French) and auto-detection is already the default behavior. This is real, not aspirational — `Transcript.language`/`language_probability` are populated from Whisper's own `info` object every run.
- **Detected language IS persisted, but only half of it.** `SpeechTranscript.language_code` (`database/models/audio.py`) is a real column, populated correctly (`app/services/pipeline_service.py:123`: `language_code=speech_result.language() or "en"`). `SpeechTranscript.language_probability` is also a real column with a doc comment ("Whisper's confidence in the detected language") but is **never actually written** — `pipeline_service.py`'s `SpeechTranscript(...)` construction omits it entirely, so it silently stays at its column default. A real, narrow bug, not a design question — same class of gap prior sprints have found and fixed (a column exists, the write path just never populates it).
- **The real design question: `task="transcribe"` vs `task="translate"`.** Whisper supports both natively. `"transcribe"` (today's default) produces text *in the spoken language* — a Spanish voice note produces Spanish text. `"translate"` produces English text directly, regardless of the spoken language. Every downstream consumer of the transcript — the extraction prompt (`extraction/prompts/system_prompt.txt`/`builder.py`, written entirely in English, with no language-handling instructions at all — confirmed by inspection, zero mentions of "language" or "English" anywhere in either file) and the 4 document-generation prompts (`generation/prompts/*.md`, daily reports/customer updates/safety talks/material reminders, all presumably written assuming English input, not yet re-checked deliverable-by-deliverable) — has never been exercised against non-English input. Feeding Spanish transcript text into an English-only extraction prompt today would very plausibly produce degraded or unpredictable extraction, not a clean failure — this needs live verification with a real non-English audio sample before any scope decision here is trusted.
- **No per-request language/task override exists.** `app/api/v1/audio.py`'s upload endpoint takes no language parameter — the whole pipeline uses one process-wide `TranscriptionConfig` default for every upload, regardless of the actual speaker. A multi-language product plausibly needs either a per-upload choice (foreman picks their language, or it's inferred from their `User`/`Worker` profile) or a fully automatic `task="translate"`-always approach (simpler, but throws away the original-language transcript entirely, which may itself be a compliance/audit concern for legal records).

**What this means for scope:** the transcription layer needs almost no new code (arguably none, if the answer to the design question is "flip a config default"), but the real work is (a) deciding and implementing the transcribe-vs-translate strategy, informed by a live test against real non-English audio to see what actually happens today, (b) fixing the `language_probability` persistence gap while touching this code anyway, and (c) verifying — not assuming — that the extraction and generation prompts handle whatever text they end up receiving.

What already exists and should NOT be rebuilt:
- `speech/whisper/engine.py`'s Whisper integration — real, working, multilingual-capable. This sprint configures and verifies it, does not replace it.
- `SpeechTranscript.language_code`/`language_probability` (Sprint 6 or earlier) — real columns; one already correctly populated, the other needs its write-path fixed, not new schema.
- `TranscriptionConfig` (`speech/config.py`) — already has `language`/`task` fields; this sprint changes what values are used and how they're chosen, not the config shape itself.
- The 4 document-generation services (Sprint 5) and their prompts (`generation/prompts/*.md`) — read, don't rewrite, unless live verification finds a real bug when non-English-sourced (or translated) content flows through them.

## Deliverables

### 1. Decide and Implement the Transcribe-vs-Translate Strategy

- Before choosing, verify live: run a real non-English audio sample (even a short synthetic or recorded Spanish/Portuguese clip) through the actual pipeline with today's `task="transcribe"` default, and inspect what `extraction/pipeline.py` actually produces from that non-English transcript text — does the extraction prompt cope reasonably, degrade gracefully, or produce garbage? This finding should directly inform the decision, not be skipped in favor of assuming the answer.
- Decide explicitly: (a) switch the global default to `task="translate"` (simplest — every transcript arrives in English regardless of spoken language, extraction/generation code needs zero changes) vs. (b) keep `task="transcribe"` and instead translate the *extracted structured data* or *generated documents* after the fact (preserves the original-language transcript for audit/compliance purposes, but is more code and a second translation step) vs. (c) make it per-upload configurable and pass through untranslated non-English text to extraction, accepting some quality degradation as a known limitation for this sprint. Document whichever is chosen as an ADR — this is exactly the kind of "real is-this-actually-a-problem investigation" prior sprints have insisted on before implementing, not a default to assume.
- If per-upload configurability is chosen (option (c), or a language hint for (a)/(b)): decide where the language selection comes from — a new optional field on `POST /audio/upload`, a `Worker.preferred_language` field (doesn't exist today — would be new schema, needs its own justification), or continued full auto-detection with no user input at all (simplest, and Whisper's auto-detection is already real and working, so this may be sufficient without adding a new field).

### 2. Fix `language_probability` Persistence

- A small, contained bug fix (not really a "deliverable" on its own, but real and worth doing precisely because Deliverable 1 already touches this exact code path): `speech/models/processing_result.py`'s `ProcessingResult` class has a `language()` method (returns `self.transcript.language`) but **no equivalent `language_probability()` method**, even though `Transcript.language_probability` is a real, populated field one layer down (`speech/whisper/engine.py` sets it from Whisper's own `info.language_probability`) — confirmed by direct inspection, not assumed. Add a `language_probability()` method to `ProcessingResult` mirroring `language()`'s exact pattern, then wire `app/services/pipeline_service.py`'s `SpeechTranscript(...)` construction to pass `language_probability=speech_result.language_probability()` alongside the already-correct `language_code=speech_result.language() or "en"`. Live-verify: run a real audio file through the pipeline and confirm the persisted `SpeechTranscript` row has a non-default `language_probability`, not just that the code compiles.

### 3. Verify Extraction and Generation Handle the Chosen Strategy's Output

- Whatever Deliverable 1 decided, live-verify it end-to-end with a real non-English audio sample (or a hand-written non-English transcript string fed directly to `ExtractionPipeline.extract()` if a real audio sample is impractical to obtain) producing a correctly-extracted `ConstructionDailyLog` and, from that, correctly-generated documents (at minimum the daily report — the other 3 service types are lower-priority for this specific check unless the first one surfaces a real problem worth generalizing from).
- If Deliverable 1 chose `task="translate"` (or a post-extraction translation step), this deliverable is mostly confirming that decision actually works end-to-end, not additional design work. If Deliverable 1 chose to pass through non-English text as-is, this deliverable's job is characterizing exactly what breaks or degrades, and deciding whether that's an acceptable known-limitation for this sprint or requires a prompt change (e.g. explicitly telling the extraction LLM "the transcript may be in any language; always respond in English regardless of input language" — Groq's models are themselves multilingual, so this is a plausible low-cost mitigation worth testing before assuming a bigger fix is needed).

### 4. Frontend: Surface Detected Language (If Useful)

- A minimal, likely-small UI addition: if `SpeechTranscript.language_code`/`language_probability` are populated and meaningful, consider surfacing detected language somewhere reviewer-facing (e.g. `RecordPage.tsx`'s status view, or the log review page) — useful context for a reviewer deciding whether an extraction looks off because of a language-handling issue vs. a genuine transcription error. Decide during implementation whether this earns its own UI real estate or is better left as backend-only data for now; this is explicitly the lowest-priority deliverable of the four and can be cut if the first three deliverables consume the sprint's real effort.

## Constraints

- **No paid APIs, no paid SaaS, no new AI/LLM calls beyond what already exists** — faster-whisper (local) already does transcription/translation; Groq (already in use) already handles extraction/generation. This sprint configures and verifies existing AI capability, it does not add a new AI service or model.
- **Sprint 1–15 FROZEN.** Extend `speech/`/`app/`/`extraction/`/`frontend/`; do not rewrite the Whisper integration, the extraction pipeline, or any generation service unless fixing a verified bug (see `docs/CONTRIBUTING.md` §5) — the `language_probability` persistence gap (Deliverable 2) qualifies as exactly this.
- **New schema requires an ADR**, matching every prior sprint's precedent — a `Worker.preferred_language` field (if Deliverable 1 needs it) is a real, documented schema decision, not a default to add silently.
- **Continue the "explain, implement, test, verify" per-subsystem discipline**, live verification over mock-based tests — this sprint's entire premise (does non-English input actually work today, and does the chosen fix actually help) is unverifiable without running a real non-English audio sample through the real pipeline. A synthetic/TTS-generated clip is an acceptable substitute if a real recorded sample isn't available, as long as it's genuinely non-English speech, not silence or noise.

## Explicit Out of Scope for Sprint 16

- Any language beyond verifying Spanish specifically works end-to-end — Portuguese/Mandarin/French are named by the roadmap but Whisper's own multilingual training presumably covers them similarly; this sprint verifies the *mechanism* works for one real non-English language, not each of the four individually, unless Spanish verification surfaces a language-specific problem worth checking against others.
- Translating already-existing historical logs/documents retroactively — this sprint's changes affect new audio uploads going forward only.
- A `Worker.preferred_language` field and any UI for setting it, unless Deliverable 1's investigation concludes per-upload language selection is genuinely needed (see that deliverable's own scoping note) — default to full auto-detection (already real and working) unless a concrete reason emerges to need explicit user input.
- Non-English UI/localization of the React frontend itself (Dashboard, Record page, etc.) — this sprint is about the voice-to-document pipeline handling non-English *speech*, not translating the product's own interface. A distinct, much larger effort not named by this roadmap item.
- Real-time/streaming transcription or live language switching mid-recording — out of scope, no prior sprint has built streaming transcription and this one doesn't need to.
