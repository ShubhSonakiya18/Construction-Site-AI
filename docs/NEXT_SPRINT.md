## Sprint 14 Goal

Per `docs/ROADMAP.md`'s Phase 4 plan: daily cost tracking, budget variance alerts, cost prediction (earned value management), and change order tracking.

**This sprint is materially different from Sprint 13, and that difference must shape every deliverable below.** Sprint 13 was pure aggregation over data that was already normalized (`LogSafetyIncident`, `LogWorkItem`, `LogDelay` — real tables, real columns, real foreign keys). Cost data is not in that state today — but the gap is narrower and more precisely located than it first appears. Trace the full path before assuming a schema problem:

- `DailyLog.financials` (`database/models/daily_log.py`) is an unstructured, nullable JSON column at the ORM/DB layer — no migration gives it real columns.
- **`financials` and the full `client_communication.change_orders` array ARE already fully defined, with real types, enums, and field-level validation, in `knowledge/construction_daily_log_schema.json`** — the actual JSON Schema `extraction/validators/schema_validator.py`'s `SchemaValidator` validates every extraction result against (`ValidationPipeline` reads `kb.raw_schema` from this exact file). `financials` has 8 properties (`daily_labor_cost_usd`, `daily_material_cost_usd`, `daily_equipment_cost_usd`, `daily_subcontractor_cost_usd`, `daily_total_cost_usd`, `cumulative_spend_to_date_usd`, `budget_remaining_usd`, `financial_notes`), each typed and bounded (`"minimum": 0` on every cost field). Its own schema `description` says, verbatim: *"Primarily populated by the cost tracking module (future sprint)."* This file was written anticipating this exact sprint. `client_communication.change_orders` is equally complete: `change_order_id`, `description`, `estimated_cost_impact_usd`, `estimated_schedule_impact_days`, and a real approval-lifecycle `status` enum (`pending_approval` | `approved` | `rejected` | `under_negotiation`).
- **The gap is one file: the LLM is never asked for either field.** `extraction/prompts/builder.py`'s `_build_schema_reference()` — the actual text block sent to Groq describing what to extract — has no `financials` key at all, and its `client_communication` block only asks for `contact_made`/`contact_method`/`customer_concerns`/`change_orders_discussed` (a boolean) — not `client_concerns` or the real `change_orders` array the JSON Schema defines. The prompt builder's hand-written reference has quietly drifted out of sync with the schema it's meant to represent; nothing enforces the two stay aligned. Since `SchemaValidator` validates against the *full* schema file regardless of what the prompt asked for, if the LLM ever did return `financials` or a real `change_orders` array, it would pass validation and persist cleanly — `DailyLogRepository.create_from_extraction_result()` already reads `financials=extracted_log.get("financials")` (`database/repositories/daily_log.py:698`) and `client_communication` wholesale. **Nothing downstream of the prompt needs to change for the LLM to start producing either field** — only the prompt itself.
- The only place `financials` is ever populated today is the hand-written seed data (`database/seed/sample_data.py:369`, 3 of the 8 fields) — because no real voice transcript has ever been asked to produce it. `change_orders` is seeded as `[]` for the same reason.
- `dataset_generation_framework/generators/daily_log_generator.py`'s `_build_financials()` (a **separate, disconnected** synthetic-training-data generator, not the live pipeline) independently fabricates the same 8-field shape and validates its internal math (`VAL-FIN-001`: `daily_total_cost_usd` sums its components) — corroborating evidence the shape in `construction_daily_log_schema.json` is the intended one, not proof the live pipeline uses it.
- Real, already-structured cost data also exists from prior sprints, independent of extraction: `LogMaterialUsed.quantity_used` × `unit_cost_usd` (Sprint 6, real columns, real seeded values — `$6.85`/`$42.00` per unit on the sample log). `PurchaseOrder.quantity_ordered` × `unit_cost_usd` (Sprint 12) gives committed-but-not-yet-consumed spend. `Project.contract_value_usd` (Sprint 6, seeded at `$425,000.00`) gives the budget side of a budget-vs-actual comparison. **No labor-rate or equipment-rate field exists anywhere in the schema** — `LogTradeOnSite.workers_count`/`hours_worked` records labor presence, not labor cost; a foreman-reported total (via the now-prompted `financials.daily_labor_cost_usd`) is the only way labor cost could ever reach this system without a much bigger payroll-integration effort.

**What this means for scope:** this sprint is centered on **extending the extraction prompt to close a known, well-scoped, already-anticipated gap** — not designing new schema from nothing. `financials` and `change_orders` need no ADR for their *shape* (the schema file already settled that); what needs deciding is the smaller set of things the schema file doesn't already answer: how the prompt should be worded to elicit these numbers reliably from a spoken transcript, whether `cumulative_spend_to_date_usd`/`budget_remaining_usd` should be left to the LLM (unreliable — it has no memory of prior logs) or computed server-side at read time instead (the established "read-time-only projection" pattern from Sprints 11–13), and whether `financials` should stay a JSON blob or get normalized into real columns/a table now that it's actually going to be populated.

What already exists and should NOT be rebuilt:
- `GET /projects/{id}/analytics` (Sprint 10, extended through Sprint 13) — the established single-response-object pattern for project-level read-only aggregation. Cost fields plausibly extend this same response rather than a new endpoint, unless a deliverable's data volume or update cadence argues otherwise (decide explicitly, document as an ADR either way, matching every Sprint 13 deliverable's own discipline).
- `LogMaterialUsed`/`PurchaseOrder` (Sprints 6/12) — real, structured, already-tenant-scoped material cost data. `InventoryRepository`/`DailyLogRepository` are the existing repositories that own these tables.
- `Project.contract_value_usd` — the one real "budget" figure in the schema today. A single total, not a phased/line-item budget — any "budget variance" deliverable can only compare against this one number, not a per-stage or per-trade budget breakdown, unless new schema is added to support that (a real decision, see Deliverable 2).
- ADR-005/ADR-007/ADR-048's "no AI where deterministic logic suffices" posture — cost math (sums, variances, EVM formulas) is pure arithmetic, matching every financial/schedule computation in this codebase so far. This does not mean AI has no role this sprint — see Deliverable 1's extraction question — only that computing *from* recorded numbers is never itself an AI call.

## Deliverables

### 1. Daily Cost Tracking — Close the Prompt Gap, Then Decide Persistence

- **This is a smaller change than it first looks.** `knowledge/construction_daily_log_schema.json` already fully defines `financials` (8 typed/bounded fields), and `SchemaValidator` already validates against that full file. The only reason no real log has ever had a populated `financials` is that `extraction/prompts/builder.py`'s `_build_schema_reference()` — the text block actually sent to Groq — never mentions it. The core of this deliverable is adding a `financials` block to that prompt (matching the style of the existing `weather`/`workforce`/`safety` blocks) so the LLM is asked for `daily_labor_cost_usd`, `daily_material_cost_usd`, `daily_equipment_cost_usd`, `daily_subcontractor_cost_usd`, and `financial_notes` when the transcript mentions cost figures. Everything downstream (`DailyLogRepository.create_from_extraction_result()`, the DB column, `GET /daily-logs/{id}`) already reads/writes `financials` wholesale — verify this live with a real transcript that mentions a dollar figure before assuming it, the same "trust but verify the actual persisted row" discipline every prior sprint has applied.
- Leave `cumulative_spend_to_date_usd`/`budget_remaining_usd` out of the prompt — a single transcript has no way to know a running total across prior logs, and asking the LLM to guess invites confidently wrong numbers. Those two fields are Deliverable 2's territory: computed server-side at read time from the sum of prior approved logs' `daily_total_cost_usd`, the same "read-time-only projection, never persisted" pattern Sprint 11's schedule variance and Sprint 12's lead-time warnings established. Decide whether to still write `null` into those two JSON keys or omit them from the persisted row entirely — either is defensible, but document which.
- `daily_total_cost_usd` — decide whether the LLM reports it directly (risk: may not sum correctly against what it separately said for labor/material/equipment/subcontractor, the exact failure mode `dataset_generation_framework`'s own `VAL-FIN-001` check exists to catch) or whether it's always server-computed as the sum of the four components after extraction (more reliable, trivial arithmetic, no reason to trust an LLM's addition when the app can just do it). The safer default: compute it server-side, don't ask the LLM for it at all.
- Real material cost (`LogMaterialUsed.quantity_used × unit_cost_usd`) is already available today with zero extraction changes — decide whether Sprint 14's "daily cost tracking" analytics field sources material cost from this real structured data (more accurate, already trustworthy) or from the LLM's own `daily_material_cost_usd` guess (consistent with the other three cost categories, but a second, possibly-disagreeing estimate of the same thing). Recommend the former for material specifically, since real data beats an LLM estimate whenever both exist for the same number — document whichever is chosen.
- `financials` stays a JSON column, not a new table — unlike `change_orders` (Deliverable 4), a `financials` row has no independent identity, lifecycle, or need for cross-log querying by its own primary key; it is one object per log, exactly the shape `weather`/`tomorrow_plan` already use successfully as JSON. Normalizing it into real columns would only be justified if a deliverable here needs to `GROUP BY`/index on an individual cost field at scale — check whether Deliverable 2/3's actual queries need that before deciding either way, and document the decision.

### 2. Budget Variance Alerts

- `Project.contract_value_usd` is a single total — decide explicitly whether "budget variance" means cumulative actual-spend-to-date vs. this one number (simple, honest about what the schema supports) or a phased/per-stage budget comparison (would need new schema — a budget isn't recorded anywhere per-stage today, only the project total). Default to the former unless a concrete, cheap way to do the latter emerges from Deliverable 1's decisions.
- "Alert" — decide what this actually means given this codebase has no scheduler (Sprint 11's resume-audit finding: no Celery Beat exists, still true) and no email/notification infrastructure beyond the customer-update document flow (Sprint 5) and password-reset emails (Sprint 9). A real-time push notification or scheduled digest is out of scope without new infrastructure this sprint doesn't call for. The realistic scope: a computed-at-read-time flag/field on the existing analytics response (e.g. `budget_variance_status: "on_track" | "over_budget" | "no_budget_set"`), the same "read-time projection, never persisted" pattern Sprint 11's schedule variance and Sprint 12's lead-time warnings already established — not a new alerting subsystem.

### 3. Cost Prediction (Earned Value Management)

- Real EVM has defined terms — Planned Value (PV), Earned Value (EV), Actual Cost (AC), Cost Performance Index (CPI = EV/AC), Schedule Performance Index (SPI = EV/PV). Before implementing, map each onto what this schema can actually compute: EV plausibly derives from `Project.contract_value_usd × overall_project_completion_percent` (Sprint 10's own completion-trend field) or from Sprint 11's schedule-based percent-complete — decide which and document why, since they can disagree. AC derives from Deliverable 1's actual cost tracking, whatever it ends up covering. PV derives from Sprint 11's `ProjectSchedule`/`ScheduleTask` planned dates, assuming linear cost accrual against the schedule (a real simplifying assumption — document it as an ADR the way ADR-055 documented "productivity"'s own necessary simplification).
- This is squarely deterministic arithmetic over already-computed values (ADR-005/007/048's posture) — no AI call for the EVM math itself, same as everything else in this analytics area.

### 4. Change Order Tracking

- **Also a prompt gap, not a from-scratch design problem — but with a real normalization decision on top.** `client_communication.change_orders` is fully defined in `knowledge/construction_daily_log_schema.json`: `change_order_id`, `description`, `estimated_cost_impact_usd`, `estimated_schedule_impact_days`, and a `status` enum (`pending_approval` | `approved` | `rejected` | `under_negotiation`) — a real approval lifecycle, already designed. The extraction prompt's `client_communication` block only asks for `contact_made`/`contact_method`/`customer_concerns`/`change_orders_discussed` (a boolean) — it needs the same treatment as Deliverable 1's `financials` gap: add `change_orders` (and, while touching this block, `client_concerns` — the schema defines it too and the prompt is currently missing it as well) to `_build_schema_reference()`.
- **The real decision this deliverable adds beyond Deliverable 1's:** a change order has its own lifecycle (`status` transitions from `pending_approval` onward) and plausibly needs cross-log reporting ("total approved change-order value this project," "change orders still pending approval") — the kind of query a JSON array buried inside another JSON column (`client_communication.change_orders`) answers only by scanning every log. Decide explicitly: keep it JSON (cheap, consistent with how `financials` is being left as JSON in Deliverable 1, correct if "tracking" this sprint means no more than "surface what was said," matching how thin the roadmap's own naming is) vs. a real normalized `LogChangeOrder` table with its own `daily_log_id` FK, matching `LogDelay`/`LogSafetyIncident`'s existing pattern (justified if a status can change *after* the log that reported it — e.g. an owner approving next week a change order discussed today — since a JSON array on an already-approved, frozen `DailyLog` row has no natural place to record that transition without either mutating an approved log's JSON in place, which nothing else in this codebase does, or writing a duplicate/superseding log entry, which is awkward). **This status-mutability question is the actual deciding factor — resolve it explicitly and write the ADR before choosing a representation, not after.**

## Constraints

- **No paid APIs, no paid SaaS, no new AI/LLM calls for cost *computation*.** Extending the extraction prompt (Deliverables 1 and 4) is not a new AI capability — extraction already calls Groq for every other section; this only widens what one existing call is asked for. Computing trends, variances, or EVM figures *from* recorded numbers (Deliverables 2–3) must stay deterministic, matching ADR-005/ADR-007/ADR-048's posture.
- **Sprint 1–13 FROZEN.** Extend `app/`/`database/`/`extraction/`/`frontend/`, do not rewrite Sprint 6's `financials`/`client_communication` column definitions, Sprint 10–13's analytics endpoint, or any other prior sprint's code unless fixing a verified bug (see `docs/CONTRIBUTING.md` §5). Widening `extraction/prompts/builder.py`'s schema reference to match fields `knowledge/construction_daily_log_schema.json` already defines is an additive fix to a stale/incomplete prompt, not a rewrite of Sprint 2–4's extraction pipeline.
- **Maintain backward compatibility.** `GET /projects/{id}/analytics`'s existing fields (Sprint 10 through Sprint 13) keep their exact current shape regardless of what Sprint 14 adds alongside them.
- **New schema (beyond widening the extraction prompt) requires an ADR, not silent assumption.** `financials` and `change_orders`' *shapes* are already settled by the JSON Schema file and need no new ADR to adopt as-is — but whether `change_orders` gets normalized into a real table (Deliverable 4) is a genuine schema decision this sprint may make, unlike Sprint 13's "no new tables" constraint. Document it the same way ADR-050 documented inventory's schema shape.
- **Continue the "explain, implement, test, verify" per-subsystem discipline**, live verification over mock-based tests, for every deliverable — for Deliverables 1 and 4 specifically, this means verifying with a **real transcript through the real pipeline** that the widened prompt actually produces a populated `financials`/`change_orders` object end-to-end, not just that the prompt text changed.

## Explicit Out of Scope for Sprint 14

- Real-time budget alerts, scheduled digests, or any notification delivery mechanism — no scheduler exists (Celery Beat confirmed absent by the resume audit), and building one is a larger, separate decision than this sprint's cost-tracking focus. "Alert" this sprint means a computed status field, not a pushed notification.
- A phased or per-stage project budget — `Project.contract_value_usd` is the only budget figure the schema records; building a real budget-line-item system is a bigger feature than "cost intelligence" as named by the roadmap, unless Deliverable 2's implementation finds a cheap way to approximate it from existing data.
- Labor/equipment rate cards or a real payroll integration — no rate field exists anywhere in the schema; Deliverable 1's `daily_labor_cost_usd`/`daily_equipment_cost_usd` are foreman-reported totals via the widened extraction prompt, not a computed rate × hours figure, since no rate table exists or is being proposed.
- A company-wide cost dashboard — Sprint 13's ADR-057 already established the per-project-only default for this app's analytics; nothing about cost data changes that reasoning, and a cross-project view remains a candidate for a later sprint unless this sprint's implementation surfaces a concrete need.
- Retroactively backfilling `financials` on any of Sprints 6–13's existing seeded/real logs that predate whatever Deliverable 1 decides — out of scope; new logs going forward are what this sprint's pipeline changes (if any) would affect.
