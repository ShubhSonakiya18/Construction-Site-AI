## Sprint 15 Goal

Per `docs/ROADMAP.md`'s Phase 5 (the phase after Sprint 14 completed Phase 4): "Daily log → automatic OSHA 300 log entries. Incident report generation. Safety trend analysis and proactive warning."

**Read the real OSHA 300/301 requirements against what this schema actually has before assuming a clean mapping exists.** It doesn't, fully — this sprint needs real gap-filling, not pure aggregation like Sprint 13, and not "widen an existing prompt" like most of Sprint 14. Investigated before writing this spec:

- **OSHA Form 300 (Log of Work-Related Injuries and Illnesses)** requires, per recordable case: a case number, employee name, job title, date of the event, where it occurred, a description, a classification into exactly one of **death / days away from work / job transfer or restriction / other recordable case**, the number of days away and number of days of job transfer/restriction, and a checkbox classification into **injury / skin disorder / respiratory condition / poisoning / hearing loss / all other illnesses**.
- **What `LogSafetyIncident` (Sprint 6, now actually populated after the pre-Sprint-15 fix) has today:** `incident_type` (`first_aid | medical_treatment | lost_time_injury | near_miss | property_damage | environmental | equipment_damage` — a severity/category triage, not OSHA's required classification), `description`, `worker_involved` (**free text**, `String(200)`, not a foreign key to `Worker`), `time_of_incident`, `body_part_affected`, `osha_recordable` (boolean, already exists), `medical_treatment_required`, `incident_reported_to`, `corrective_actions`. **No case number, no days-away count, no days-of-restriction count, no OSHA classification (death/days-away/transfer/other), no injury-type checkbox category, no date-of-event column (inherited from the parent `DailyLog.log_date` instead — usually correct, but an incident described in a log written the day after it happened would misattribute the date).**
- **`worker_involved` being free text, not a `Worker` FK, is a real problem for this sprint specifically** — OSHA 300 requires the employee's actual job title, which this schema only has on the real `Worker` record (`role` column), not on a free-text name string extracted from a voice transcript. A voice log saying "Miguel twisted his ankle" gives no reliable way to look up which `Worker` row "Migual" [sic — a name may be misheard/mis-transcribed] refers to.
- **No `Worker` linkage exists anywhere in the daily-log extraction path today** — `LogTradeOnSite`'s own doc comment (`database/models/worker.py`) already flags this as a known gap: *"worker_identifier in log_trades_on_site is a free-text field from voice recordings — it is linked to Worker.id via the repository layer when an exact name match is found"* (i.e., a best-effort fuzzy match already exists for trades-on-site; confirm during implementation whether `LogSafetyIncident.worker_involved` should reuse that same matching logic, or whether OSHA-compliance-grade data needs a stricter standard than "best effort" given the legal stakes of an official government form).
- **PDF generation exists (Sprint 10, `app/services/pdf_export.py`) but is deliberately narrow and does not fit this sprint's needs as-is.** `render_markdown_pdf()` parses only the specific Markdown shape (`##` headers, `**bold**`, `- ` bullets) the 4 existing document-generation services produce — it has no table-rendering path. An OSHA 300 Log is fundamentally tabular (one row per case, fixed columns), which this function's design doesn't support. `reportlab` (the library already in use) has a real `Table`/`TableStyle` API (`reportlab.platypus`) capable of rendering this, but it means writing a second, separate PDF-generation code path for this sprint — not reusing or extending `render_markdown_pdf()`, which stays exactly what it is for the 4 document types it already serves.

**What this means for scope:** this sprint cannot be "compute a report from existing columns" the way most of Sprint 13 was. It needs (a) new columns on `LogSafetyIncident` capturing OSHA's actual classification scheme, (b) a real decision about `worker_involved`'s reliability for an official compliance document, and (c) new PDF-table-rendering code, not a reuse of Sprint 10's exporter. Each of these is a genuine, document-worthy decision — do not silently assume any of them away.

What already exists and should NOT be rebuilt:
- `LogSafetyIncident`/`LogHazard` (Sprint 6, database/models/log_items.py) — real tables, real tenant-scoped repository methods, now actually populated by real extraction (post-fix). Extend with new columns via a migration; do not replace.
- `get_safety_incident_trend_scoped()`/`get_safety_incident_breakdown_scoped()` (Sprint 13, `DailyLogRepository`) — the existing safety-analytics aggregation on `GET /projects/{id}/analytics`. "Safety trend analysis" (this sprint's third named goal) is largely already built; confirm during implementation whether it needs anything beyond what Sprint 13 shipped, or whether "proactive warning" (see below) is the only genuinely new trend-analysis work.
- `app/services/pdf_export.py`'s `render_markdown_pdf()` — reused only for its general reportlab setup patterns (fonts, page size, margins) if convenient; not extended to handle tables. A new function in the same module (or a new module) for the OSHA-form-specific table rendering is the cleaner fit, given how narrowly-scoped the existing function's own docstring says it is.
- ADR-005/ADR-007/ADR-048's "no AI where deterministic logic suffices" posture — classifying an already-recorded incident into OSHA's death/days-away/transfer/other categories, and generating the PDF table itself, are both deterministic once the right input fields exist. This does not mean zero AI role this sprint — see Deliverable 1's extraction question, the same shape of decision Sprint 14's Deliverable 1 faced for `financials`.

## Deliverables

### 1. OSHA-Classification Data Capture — Extend `LogSafetyIncident`, Then the Extraction Prompt

- New migration adding to `log_safety_incidents`: an OSHA classification field (`death | days_away_from_work | job_transfer_or_restriction | other_recordable_case`, nullable — not every incident is even OSHA-recordable, matching how `osha_recordable` already stays nullable for "not yet assessed"), an injury-type category (`injury | skin_disorder | respiratory_condition | poisoning | hearing_loss | all_other_illnesses`, nullable), `days_away_from_work_count` (integer, nullable), `days_of_job_transfer_or_restriction_count` (integer, nullable), and a `case_number` (string, nullable — OSHA logs are typically numbered sequentially per calendar year per establishment; decide during implementation whether this is foreman-reported, auto-assigned at read time, or left for a human to fill in later, since none of Sprints 6–14 have any per-year sequence-numbering precedent to reuse).
- Decide explicitly, matching Sprint 14 Deliverable 1's exact question: does the extraction prompt get widened to ask the LLM for these fields directly from the transcript (a foreman is unlikely to naturally say "this is a days-away-from-work case" in casual speech, unlike a dollar figure — recommend against extracting the OSHA classification itself via LLM, since it is a specific legal/regulatory determination, not an observed fact a foreman would state), versus leaving classification as a human-entered field on an existing incident (e.g. a new `PATCH /daily-logs/{id}/safety-incidents/{incident_id}` endpoint a safety officer uses after the fact, matching how Sprint 12's `PurchaseOrder.status` and Sprint 14's `LogChangeOrder.status` are both human-updated after initial extraction, not LLM-guessed). The recommended default: `days_away_from_work_count`/`days_of_job_transfer_or_restriction_count` may be voice-extractable if a foreman states them ("he'll be out for about a week"); the death/days-away/transfer/other classification itself should be human-entered, not LLM-inferred, given the legal weight of a government compliance form being wrong.

### 2. Worker Identification for OSHA Records

- Decide explicitly whether `LogSafetyIncident` gains a nullable `worker_id` FK to `Worker` (populated via the same best-effort name-matching `LogTradeOnSite.worker_identifier` already uses, per that column's own doc comment) or whether `worker_involved` stays free text with job title left blank/manually filled on the eventual PDF. Given OSHA 300 legally requires job title, and a wrong or unmatched name is worse than an honestly-blank field on a government form, recommend: attempt the match, but do not silently treat a low-confidence or failed match as ground truth — surface unmatched incidents as needing human review before they can appear on a generated OSHA 300 Log (see Deliverable 4).

### 3. OSHA 300/301 PDF Generation

- A new PDF-generation code path (not an extension of `render_markdown_pdf()`, per the investigation above) using `reportlab.platypus.Table`/`TableStyle`, producing the real OSHA 300 Log's column layout for a project's (or company's — decide scope, matching Sprint 13's ADR-057 per-project-vs-company-wide precedent) recordable incidents in a given calendar year. OSHA Form 301 (Injury and Illness Incident Report) is a single-incident detail form, not a log — decide during implementation whether both 300 and 301 are in scope for this sprint or whether 301 (one PDF per incident, on demand) is a reasonable follow-on cut if time is tight, and document whichever choice is made.
- An incident missing required data (no classification, no matched worker/job title) should be either excluded from the generated PDF with a clear "N incidents need review before inclusion" message, or included with explicit blank/TBD markers — decide and document which, since silently omitting a real recordable incident from an official compliance document is the kind of gap a real safety officer needs to know about, not one that should be invisible.

### 4. Safety Trend Analysis and Proactive Warning

- Sprint 13 already ships `safety_incident_trend`/`safety_incident_breakdown` on `GET /projects/{id}/analytics` — confirm during implementation whether that's sufficient for "trend analysis," or whether this sprint adds something genuinely new (e.g. a rolling recordable-incident-rate figure, which OSHA itself computes via a standard formula: `(recordable cases × 200,000) / total hours worked` — decide whether `LogTradeOnSite.hours_worked`'s aggregate across a project gives a real, trustworthy hours-worked denominator for this, or whether that figure is too incomplete to support a real OSHA incidence-rate calculation without overstating precision).
- "Proactive warning" — matching Sprint 14 Deliverable 2's exact resolution for "budget variance alerts": this codebase has no scheduler and no notification infrastructure, so a "warning" this sprint means a computed field/flag on a read (e.g. "3 unresolved high-severity hazards older than 7 days" surfaced on the existing analytics response, or a project-level "days since last incident" figure), not a pushed notification. Do not silently expand scope to build alerting infrastructure — that is a separate, much larger decision this sprint's constraints don't call for, the same reasoning Sprint 14 already applied to the identically-shaped "budget alert" ask.

## Constraints

- **No paid APIs, no paid SaaS.** No new AI/LLM calls for OSHA classification itself (Deliverable 1 recommends against LLM-inferred legal classification) or for trend/warning computation (Deliverable 4) — matches ADR-005/ADR-007/ADR-048's posture. Extraction-prompt widening (if Deliverable 1's days-away/restriction counts are voice-extracted) is not a new AI capability, the same reasoning Sprint 14 applied to its own prompt changes.
- **Sprint 1–14 FROZEN.** Extend `database/`/`app/`/`extraction/`/`frontend/`; do not rewrite Sprint 6's `LogSafetyIncident`/`LogHazard` models, Sprint 10's `render_markdown_pdf()`, Sprint 13's safety-analytics aggregation, or any other prior sprint's code unless fixing a verified bug (see `docs/CONTRIBUTING.md` §5) — the pre-Sprint-15 safety-prompt fix already landed as exactly this kind of verified, documented bug fix, not a Sprint 15 deliverable.
- **New schema requires an ADR**, matching Sprint 14's own precedent — the new `LogSafetyIncident` columns (Deliverable 1) and the `worker_id` FK decision (Deliverable 2) are real schema-shape choices, not assumed defaults.
- **Maintain backward compatibility.** `GET /projects/{id}/analytics`'s existing fields (Sprint 10 through Sprint 14) keep their exact current shape regardless of what Sprint 15 adds alongside them.
- **Continue the "explain, implement, test, verify" per-subsystem discipline**, live verification over mock-based tests, for every deliverable — for Deliverable 3 specifically, this means opening the actual generated PDF and confirming its table renders correctly with real data, not just that the endpoint returns 200 with a PDF-shaped byte stream.

## Explicit Out of Scope for Sprint 15

- Real notification/alerting infrastructure for "proactive warning" — a computed field on a read, not a pushed notification (no scheduler exists; see Deliverable 4).
- A real payroll/HR system integration for `Worker` job-title/hire-date accuracy — this sprint uses whatever `Worker.role` already records; improving `Worker` data quality itself is a different, unrelated effort.
- Hazard-to-OSHA-form mapping — OSHA 300/301 are specifically about recordable *incidents* (injuries/illnesses), not the separate `LogHazard` (identified-but-not-yet-incident) table. `LogHazard` stays exactly as Sprint 13's own scoping note ("Sprint 13 only names incident trends, not hazards") already established — out of scope for this sprint's compliance-document work, though it remains fair game for Deliverable 4's "proactive warning" framing (an unresolved hazard is a legitimate thing to warn about, distinct from generating an official OSHA form for it).
- Multi-year OSHA log history/archival UI — this sprint generates a PDF for a given calendar year on demand; a dedicated year-over-year compliance-history browsing UI is a larger, separate feature.
- Auto-submission of OSHA forms to any government system or API — no such integration exists or is being proposed; this sprint produces a PDF a human still reviews and files themselves, the same "human still does the last mile" posture Sprint 12's purchase-order "preparation only" scoping (ADR-050) already established for supplier integration.
