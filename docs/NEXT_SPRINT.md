## Sprint 14 Goal

Per `docs/ROADMAP.md`'s Phase 4 plan: daily cost tracking, budget variance alerts, cost prediction (earned value management), and change order tracking.

**This sprint is materially different from Sprint 13, and that difference must shape every deliverable below.** Sprint 13 was pure aggregation over data that was already normalized (`LogSafetyIncident`, `LogWorkItem`, `LogDelay` — real tables, real columns, real foreign keys). Cost data is not in that state:

- `DailyLog.financials` (`database/models/daily_log.py`) is an **unstructured, nullable JSON column** — doc comment says "Object with `daily_labor_cost_usd`, `daily_material_cost_usd`, `daily_equipment_cost_usd`, etc." No Pydantic model defines its shape on the live path. No migration gives it real columns.
- **The live AI extraction pipeline never populates it.** Confirmed by reading `extraction/models/extraction_result.py` (the actual Pydantic model Groq's structured output is parsed into for a real voice log) — there is no `financials` field anywhere in it. `financials` is read and written by `DailyLogRepository.create_from_extraction_result()` (`financials=extracted_log.get("financials")`, `database/repositories/daily_log.py:698`) and exposed on `GET /daily-logs/{id}` (`app/api/v1/daily_logs.py:274`), but nothing in the actual voice-to-log pipeline ever produces a value for it. The only place `financials` is populated on the live path is the hand-written seed data (`database/seed/sample_data.py:369`) — a single log, three plain floats.
- **A fuller shape already exists, but only in the synthetic-dataset tooling, not the live pipeline.** `dataset_generation_framework/generators/daily_log_generator.py`'s `_build_financials()` (line 1037) fabricates `financials` for generated training records with 8 fields: the 3 the seed uses, plus `daily_subcontractor_cost_usd`, `daily_total_cost_usd` (computed as the sum), `cumulative_spend_to_date_usd` and `budget_remaining_usd` (both deliberately left `None` — this generator doesn't compute them either), and a free-text `financial_notes`. `dataset_generation_framework/validation/pipeline.py`'s `_check_math_consistency()` (VAL-FIN-001) even validates that `daily_total_cost_usd` sums its components correctly in generated data. **This is dataset-generation tooling, not the live extraction path** — it produces synthetic records for training/testing the extraction model, and has no connection to `extraction/models/extraction_result.py` or the real Groq call `run_pipeline()` makes for an actual uploaded voice log. Its value to this sprint is as a **already-thought-through reference shape** for `financials` (including the two derived running-total fields this sprint's own deliverables would otherwise have to invent from scratch) — not as evidence the live pipeline already handles cost data.
- `DailyLog.client_communication.change_orders` (nested inside another unstructured JSON column) has **zero defined shape anywhere** — not in the extraction model, not in a schema, not even a documented example. The seed data sets it to `[]`. It is a name and a doc-comment mention, nothing else.
- Real, already-structured cost data **does** exist in two places from prior sprints: `LogMaterialUsed.quantity_used` × `unit_cost_usd` (Sprint 6, real columns, real seeded values — `$6.85`/`$42.00` per unit on the sample log) gives real per-log material spend today, with no new schema needed. `PurchaseOrder.quantity_ordered` × `unit_cost_usd` (Sprint 12) gives committed-but-not-yet-consumed spend. `Project.contract_value_usd` (Sprint 6, real column, seeded at `$425,000.00`) gives the budget side of a budget-vs-actual comparison. **No labor-rate or equipment-rate field exists anywhere in the schema** — `LogTradeOnSite.workers_count`/`hours_worked` records labor presence, not labor cost; there is no `rate_usd` column on any table.

**What this means for scope:** "Daily cost tracking" and "change order tracking" as named by the roadmap describe data this app doesn't actually capture yet, not data sitting in a table waiting to be aggregated. Before writing a single query, each deliverable below needs an explicit decision — normalize `financials` into real tables now (a real schema change, unlike Sprint 13's "no new tables" constraint), keep querying the JSON blob as-is (cheap, but fragile — no validation, no indexing, `NULL` far more often than not until extraction actually produces it), or scope the deliverable down to what real structured data (`LogMaterialUsed`, `PurchaseOrder`, `Project.contract_value_usd`) already supports. **Do not assume normalization is the right call by default** — this sprint's own constraints (see below) lean the other way for at least some deliverables.

What already exists and should NOT be rebuilt:
- `GET /projects/{id}/analytics` (Sprint 10, extended through Sprint 13) — the established single-response-object pattern for project-level read-only aggregation. Cost fields plausibly extend this same response rather than a new endpoint, unless a deliverable's data volume or update cadence argues otherwise (decide explicitly, document as an ADR either way, matching every Sprint 13 deliverable's own discipline).
- `LogMaterialUsed`/`PurchaseOrder` (Sprints 6/12) — real, structured, already-tenant-scoped material cost data. `InventoryRepository`/`DailyLogRepository` are the existing repositories that own these tables.
- `Project.contract_value_usd` — the one real "budget" figure in the schema today. A single total, not a phased/line-item budget — any "budget variance" deliverable can only compare against this one number, not a per-stage or per-trade budget breakdown, unless new schema is added to support that (a real decision, see Deliverable 2).
- ADR-005/ADR-007/ADR-048's "no AI where deterministic logic suffices" posture — cost math (sums, variances, EVM formulas) is pure arithmetic, matching every financial/schedule computation in this codebase so far. This does not mean AI has no role this sprint — see Deliverable 1's extraction question — only that computing *from* recorded numbers is never itself an AI call.

## Deliverables

### 1. Daily Cost Tracking — Decide Where the Numbers Come From First

- **The real, unavoidable first decision:** does "daily cost tracking" mean (a) extending the AI extraction pipeline so a foreman's voice log can actually report `daily_labor_cost_usd`/`daily_material_cost_usd`/`daily_equipment_cost_usd` and have the LLM populate `financials` for the first time, or (b) computing an equivalent number deterministically from data that's already structured (`LogMaterialUsed` gives real material cost per log today; there is no equivalent structured source for labor or equipment cost), or (c) both — extraction for labor/equipment (the only way that data could ever reach the system, since no other table captures it), deterministic computation for material (already possible, no extraction needed). Constraint check before choosing: extraction changes touch `extraction/models/extraction_result.py`, the LLM prompt, and `DailyLogRepository.create_from_extraction_result()` — a materially bigger change than Sprint 13's pure-aggregation deliverables, and outside this sprint's "no AI/LLM calls for **analytics computation**" constraint only in the sense that populating the field is extraction, not analytics; computing trends *from* the field afterward must still be deterministic.
- If `financials` extraction is in scope: define its shape as a real Pydantic model (not an untyped dict) before touching the LLM prompt, matching how every other extracted section (`workforce`, `safety`, `delays`) already has one. `dataset_generation_framework/generators/daily_log_generator.py`'s `_build_financials()` is a reasonable starting shape (`daily_labor_cost_usd`, `daily_material_cost_usd`, `daily_equipment_cost_usd`, `daily_subcontractor_cost_usd`, `daily_total_cost_usd`, `financial_notes`) — decide whether to adopt it as-is or trim it; either way it's a considered reference, not a blank-slate design exercise. `cumulative_spend_to_date_usd`/`budget_remaining_usd` are deliberately left uncomputed even there — those are read-time-computed aggregates (Deliverable 2's territory), not something a single log's extraction could know on its own.
- If extraction is out of scope for this sprint (a legitimate, document-it-as-an-ADR choice given the size of that change): daily cost tracking degrades to "material cost per day, from `LogMaterialUsed`, which is real data today" — say so explicitly rather than silently narrowing what "daily cost tracking" delivers.

### 2. Budget Variance Alerts

- `Project.contract_value_usd` is a single total — decide explicitly whether "budget variance" means cumulative actual-spend-to-date vs. this one number (simple, honest about what the schema supports) or a phased/per-stage budget comparison (would need new schema — a budget isn't recorded anywhere per-stage today, only the project total). Default to the former unless a concrete, cheap way to do the latter emerges from Deliverable 1's decisions.
- "Alert" — decide what this actually means given this codebase has no scheduler (Sprint 11's resume-audit finding: no Celery Beat exists, still true) and no email/notification infrastructure beyond the customer-update document flow (Sprint 5) and password-reset emails (Sprint 9). A real-time push notification or scheduled digest is out of scope without new infrastructure this sprint doesn't call for. The realistic scope: a computed-at-read-time flag/field on the existing analytics response (e.g. `budget_variance_status: "on_track" | "over_budget" | "no_budget_set"`), the same "read-time projection, never persisted" pattern Sprint 11's schedule variance and Sprint 12's lead-time warnings already established — not a new alerting subsystem.

### 3. Cost Prediction (Earned Value Management)

- Real EVM has defined terms — Planned Value (PV), Earned Value (EV), Actual Cost (AC), Cost Performance Index (CPI = EV/AC), Schedule Performance Index (SPI = EV/PV). Before implementing, map each onto what this schema can actually compute: EV plausibly derives from `Project.contract_value_usd × overall_project_completion_percent` (Sprint 10's own completion-trend field) or from Sprint 11's schedule-based percent-complete — decide which and document why, since they can disagree. AC derives from Deliverable 1's actual cost tracking, whatever it ends up covering. PV derives from Sprint 11's `ProjectSchedule`/`ScheduleTask` planned dates, assuming linear cost accrual against the schedule (a real simplifying assumption — document it as an ADR the way ADR-055 documented "productivity"'s own necessary simplification).
- This is squarely deterministic arithmetic over already-computed values (ADR-005/007/048's posture) — no AI call for the EVM math itself, same as everything else in this analytics area.

### 4. Change Order Tracking

- `client_communication.change_orders` has no defined shape anywhere in the codebase — this is not "wire up an existing field," it is "design a field that has only ever existed as a name." Decide during implementation: a real normalized `ChangeOrder` table (a genuine, justified departure from Sprint 13's own "no new tables" constraint, since Sprint 13 could lean on tables that already existed and this data has none) vs. a defined-shape JSON object inside the existing `client_communication` column (cheaper, consistent with how `financials` was originally scoped, but inherits the same query/validation weaknesses that make `financials` hard to aggregate today). A normalized table is the more defensible choice if change orders need their own approval lifecycle, cost delta, or cross-log reporting (all plausible for "tracking"); a JSON field is defensible only if this sprint's scope is genuinely just "record that a change order was discussed," matching how thin the seed data's own example already is. Whichever is chosen, write the ADR before implementing — this is exactly the kind of schema-shape decision every prior sprint has insisted on documenting rather than assuming.

## Constraints

- **No paid APIs, no paid SaaS, no new AI/LLM calls for cost *computation*** — matches ADR-005/ADR-007's posture and every prior sprint's aggregation-over-generation choice. This does not forbid extraction-pipeline changes (Deliverable 1's option (a)/(c)) if that's the path chosen — extraction already calls the LLM; asking it to also report cost figures is not a new AI capability, just a bigger prompt. Computing trends, variances, or EVM figures *from* recorded numbers must stay deterministic.
- **Sprint 1–13 FROZEN.** Extend `app/`/`database/`/`frontend/`, do not rewrite Sprint 6's `financials`/`client_communication` column definitions, Sprint 10–13's analytics endpoint, or any other prior sprint's code unless fixing a verified bug (see `docs/CONTRIBUTING.md` §5).
- **Maintain backward compatibility.** `GET /projects/{id}/analytics`'s existing fields (Sprint 10 through Sprint 13) keep their exact current shape regardless of what Sprint 14 adds alongside them.
- **New schema requires an ADR, not silent assumption.** Unlike Sprint 13, this sprint may legitimately need new tables or new structured columns (`financials` and `change_orders` are unstructured today) — the constraint is not "no new schema," it's "document why, the same as ADR-050 did for inventory's schema shape."
- **Continue the "explain, implement, test, verify" per-subsystem discipline**, live verification over mock-based tests, for every deliverable.

## Explicit Out of Scope for Sprint 14

- Real-time budget alerts, scheduled digests, or any notification delivery mechanism — no scheduler exists (Celery Beat confirmed absent by the resume audit), and building one is a larger, separate decision than this sprint's cost-tracking focus. "Alert" this sprint means a computed status field, not a pushed notification.
- A phased or per-stage project budget — `Project.contract_value_usd` is the only budget figure the schema records; building a real budget-line-item system is a bigger feature than "cost intelligence" as named by the roadmap, unless Deliverable 2's implementation finds a cheap way to approximate it from existing data.
- Labor/equipment rate cards or a real payroll integration — no rate field exists anywhere in the schema; if Deliverable 1 extends extraction to capture labor/equipment cost, that's a foreman-reported total (`daily_labor_cost_usd`), not a computed rate × hours figure, since no rate table exists or is being proposed.
- A company-wide cost dashboard — Sprint 13's ADR-057 already established the per-project-only default for this app's analytics; nothing about cost data changes that reasoning, and a cross-project view remains a candidate for a later sprint unless this sprint's implementation surfaces a concrete need.
- Retroactively backfilling `financials` on any of Sprints 6–13's existing seeded/real logs that predate whatever Deliverable 1 decides — out of scope; new logs going forward are what this sprint's pipeline changes (if any) would affect.
